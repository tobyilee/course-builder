# 의도된 리셋 — 다른 위치 vs key prop 두 전략

> LOs: LO-S4.3

## 개요

두 명의 플레이어를 번갈아 가며 점수를 매기는 스코어보드를 만든다고 해봅시다. Taylor 차례에 10점을 쌓아두고 "Next player" 버튼을 누르면 — 어, Sarah의 점수가 10점에서 시작합니다 [slide 1]. 지난 class([S4.C1])에서 배운 규칙이 발목을 잡습니다. 같은 위치 + 같은 `Counter` 타입이라 React는 친절하게 state를 보존했을 뿐입니다. 이번엔 그 보존을 **일부러 깨뜨리는** 두 전략을 봅니다.

## 핵심 개념

**전략 1 — 다른 위치로 렌더하기** [slide 2]. 분기를 두 갈래로 나눠 트리에서 서로 다른 슬롯에 둡니다.

```jsx
{isPlayerA && <Counter person="Taylor" />}
{!isPlayerA && <Counter person="Sarah" />}
```

한 시점에는 둘 중 하나만 마운트되지만 트리 위치 자체가 다르므로 state도 분리됩니다. 단, 위치를 미리 두 개로 못박는 셈이라 분기가 이산적(A/B)일 때만 깔끔합니다.

**전략 2 — `key` prop** [slide 3]. 같은 위치라도 `key`가 바뀌면 React는 **다른 정체성의 컴포넌트**로 봅니다.

```jsx
<Counter key={isPlayerA ? 'Taylor' : 'Sarah'} person={...} />
```

`key`가 바뀌면 이전 state는 폐기되고 새로 마운트됩니다. 중요한 건 `key`가 **같은 부모 안에서만** 유일하면 충분하다는 것입니다 — 글로벌 유일성은 필요 없습니다. 리스트의 `key`와 같은 메커니즘이지만, 여기서는 의도가 "명시적 리셋"으로 다릅니다.

## 예시

스코어보드 리팩터링 [slide 4]. 전략 2를 적용하면 한 줄이면 됩니다.

```jsx
<Counter key={isPlayerA ? 'Taylor' : 'Sarah'} person={...} />
```

Next 버튼을 한 번 누르면 `key`가 바뀌어 score가 0으로 자동 초기화됩니다. 분기 두 개로 가르는 전략 1보다 코드가 짧고, "이 컴포넌트는 사람이 바�뀌면 리셋되어야 한다"는 도메인 의미를 코드가 직접 말해 줍니다.

더 실전적인 사례 — 채팅 폼 [slide 5].

```jsx
// 버그: 연락처를 바꿔도 입력 중이던 메시지가 그대로
<Chat contact={to} />

// 해법: to.id가 바뀔 때마다 폼이 새로 마운트
<Chat key={to.id} contact={to} />
```

`to.id`가 바뀌어도 `<Chat>`은 같은 위치 + 같은 타입이라 textarea state가 보존되어 버립니다. `key={to.id}` 한 줄이 "연락처별로 독립된 입력창"이라는 의미를 코드로 표현해 줍니다.

## 흔한 실수

- **동적 리스트에서 `key`를 빼먹기.** 형제로 나열되는 컴포넌트는 `key`가 없으면 React가 위치만으로 매칭해 항목 삽입·삭제 시 엉뚱한 컴포넌트로 state가 달라붙습니다.
- **배열 인덱스를 `key`로 사용.** 정렬·필터·중간 삽입이 일어나는 순간 인덱스는 같은 항목을 가리키지 않게 되어 state가 잘못된 행에 붙습니다. 안정적인 도메인 ID(`item.id`)를 쓰세요.

## 복습

의도된 리셋은 두 가지입니다 — 다른 위치로 렌더하거나, 같은 위치에 다른 `key`를 주거나. `key`는 같은 부모 안에서만 유일하면 됩니다. 다음 class([S4.C3])에서는 트리 위치 모델에서 자주 빠지는 두 함정을 봅니다.
